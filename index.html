Research: challenges in adopting AI in enterprise applications

Moving an AI prototype into a production enterprise system raises questions that demos never surface: how to secure tool access, keep context under control, choose between architectures, and prove the value. My study groups the most common challenges into five areas, with a short, answer-oriented overview of each. It is written for architects, engineering leads and product teams building or evaluating AI agents.

1. Context and Knowledge3 questions
What is context engineering, and how is it different from prompt engineering?
Prompt engineering focuses on wording a single instruction well. Context engineering is the wider discipline of deciding everything a model sees at each step: instructions, retrieved knowledge, tool definitions, memory and conversation history. In agent systems, the quality of the context usually matters more than the cleverness of the prompt. 5 min read
How do you avoid context bloat and context rot?
Stuffing the window with every tool, document and past message raises cost and latency, and it also degrades answer quality as relevant details get diluted. Keep context lean: load tools and skills only when needed, summarize or trim history, retrieve selectively, and offload large results to files or external stores.
When should you use RAG, Skills, MCP or memory?
Each solves a different problem. Use RAG (Retrieval-Augmented Generation) to ground answers in large or changing knowledge, Skills to package repeatable procedures and domain know-how, MCP (Model Context Protocol) to connect to live tools and systems, and memory to carry user or task state across sessions. Most enterprise solutions combine more than one. Read the deep dive
2. Architecture and Frameworks6 questions
Should you use a single agent or multiple agents?
Start with a single agent and add more only when you have a clear reason, such as distinct tool sets, parallel work, separate permissions or context isolation. Multi-agent designs add coordination overhead, cost and new failure modes, so the benefit must outweigh them.
Skills or MCP: which should you choose?
MCP exposes external tools and data through a standard interface, which suits live integrations and shared services. Skills encode instructions and workflows the agent loads on demand, which suits procedures and conventions. The key factors are whether you need live system access, how reusable the capability must be, and how much context it consumes.
LangGraph or create_agent: when to use which?
A prebuilt agent helper such as create_agent is the fastest route for straightforward tool-calling loops. LangGraph gives explicit control over state, branching, retries, persistence and human checkpoints, which matters for complex or long-running workflows. Pick the simplest option that meets your control and reliability needs.
How do the major agent frameworks compare?
Frameworks differ in abstraction level, orchestration model, state handling, ecosystem and production maturity. Compare them against your actual requirements: language and platform fit, multi-agent support, observability hooks, community activity and the cost of switching later.
How do you balance enterprise performance between the model and the harness?
A stronger model is not the only lever. The harness, meaning the prompts, tools, context handling, retries and evaluation loop around the model, often determines real-world accuracy and cost. Measure both together on your own tasks before upgrading either.
How do you design for scalability and high throughput?
Treat agents like any distributed workload: make steps stateless where possible, queue and parallelize work, cache repeated calls, respect model rate limits and plan for graceful degradation. Track latency, token usage and error rates per step so bottlenecks are visible early.
3. Security and Trust5 questions
How do you secure MCP: credentials, authentication and error handling?
Give agents the least privilege they need, preferring scoped, short-lived credentials and delegated user identity over shared service keys. Keep secrets out of the model’s context and authenticate at the tool layer. Return structured errors so the model can tell an identity or permission problem apart from a genuine tool failure and respond appropriately instead of retrying blindly.
How do you protect agents from security threats?
Agents introduce new risks such as prompt injection, data exfiltration through tools, excessive permissions and untrusted tool or skill sources. Defend in depth: validate inputs and outputs, sandbox execution, restrict network and data access, vet third-party tools, and log every action for audit.
How do you add guardrails and evaluators, and measure agent quality?
Guardrails constrain behavior at runtime, for example by filtering unsafe content, enforcing policies and validating outputs. Evaluators measure quality over time using test sets, rubrics and LLM-based or human review. Define what “good” means for each use case first, then automate checks against it.
How do you handle data privacy, governance and compliance?
Enterprise data brings obligations around personal data, residency, retention and auditability. Classify what can reach a model, mask or redact sensitive fields, keep audit trails of prompts and tool calls, and confirm that vendors meet your regulatory requirements.
When should a human stay in the loop?
High-impact or irreversible actions, such as payments, deletions and external communications, should require approval. Decide which actions are autonomous, which need review and which are blocked, and design the approval step so it is fast enough that people do not bypass it.
4. Reliability, Operations and Cost5 questions
How do you choose an observability framework for AI tools?
Look for end-to-end tracing of prompts, tool calls, token usage, latency and cost, plus support for open standards such as OpenTelemetry. Prefer tools that work across your frameworks and model providers, and that let you attach evaluation scores to traces.
How do you make agents reliable despite hallucinations and non-determinism?
Model output varies and sometimes errs, so reliability has to be designed in. Ground answers in retrieved sources, validate structured outputs, add retries and fallbacks, set step and time limits, and make failures visible rather than silent.
How do you test and evaluate agents in CI/CD?
Treat prompts, tools and skills like code: keep versioned regression test sets, run evaluations on every change and gate releases on quality thresholds. Compare model and prompt versions side by side to catch regressions before users do.
How do you control cost, latency and token usage?
Cost scales with context size, model choice and number of steps. Route simple tasks to smaller models, cache repeated work, trim context and set budgets, then review the trade-off between quality, speed and spend regularly.
How do you choose models and avoid vendor lock-in?
Models and prices change quickly. Keep a thin abstraction between your application and the provider, evaluate candidates on your own data, and design prompts, tools and evaluations so that switching models is a test run rather than a rewrite.
5. Building and Adoption3 questions
How do you build skills, and what are the best practices?
A good skill is focused, clearly described so the agent knows when to use it, and written with concrete instructions, examples and any supporting scripts or references. Keep each skill small, test it against real tasks, and iterate from observed failures.
How do you prove ROI and manage organizational change?
Technology alone does not deliver value. Start with a well-scoped use case, define success metrics before launch, measure against a baseline, and invest in training, trust and workflow redesign so teams actually adopt the tool.
How can you use open-source projects to grow your AI skills?
Open-source agent frameworks, MCP servers and skill libraries are a practical way to learn current patterns. Read how mature projects handle tools, state and evaluation, run and modify examples, then contribute fixes, documentation or small features.

Deep dive: Skills, MCP, RAG and Memory

With agentic AI, building software is easier and faster, but new problems appear. One of the biggest is how to extend a model with Skills, MCP, RAG and Memory. Their uses overlap, so the real question is how to choose, combine, govern and observe them to build reliable, secure and maintainable enterprise agents.

Choosing the right approachFour questions, one example

Skills provide reusable procedures. MCP provides standard access to external tools and data. RAG provides relevant knowledge at runtime. Memory keeps information and progress across interactions. Ask four questions:

  • Must the agent do something or reach a live system? Use MCP.
  • Does it need facts from a large or changing body of content? Use RAG.
  • Does it need a specific, repeatable way of working? Use a Skill.
  • Does it need to remember a user or earlier work? Use Memory.

If the knowledge is small and stable, put it in a skill’s reference file or in the prompt instead of building RAG. If you need a different style or behavior rather than new knowledge, consider fine-tuning. Start with the simplest option, add one capability at a time, and measure what each addition changes in accuracy, cost and latency.

Example: an expense assistant. A skill defines the review steps and policy checks. RAG looks up the travel policy documents. MCP connects to the finance system to submit the claim. Memory remembers the employee’s default cost center. Each answers a different question, and none replaces another.

Agent SkillsReusable procedures for repeatable tasks
What they are, and the problem they solve
A skill is a folder with a SKILL.md file (a name, a description and instructions) plus optional scripts, templates and reference files. Before skills, a long system prompt carried every instruction on every request. Instructions piled up, competed with each other, and a change in one place could break another.
How they work
Skills use progressive disclosure. At startup the agent loads only each skill’s name and description. It loads the full instructions when a skill matches the task, and reads reference files or runs scripts only if needed. One agent can carry many skills without a giant prompt. Each skill has one job, so it can be versioned, tested and reused across agents. Rule of thumb: put who the agent is and what it must always do in the system prompt, and how to do a specific task in a skill. Skills and MCP work together: a skill says how to do the job and when to use which tool, and MCP supplies the tool. Reusable skills are published by Anthropic, Copilot and Google.
In the enterprise
Domain experts hold the detailed steps, guardrails and rules, so they should write the skills.
  • Keep each skill small and focused on one job, and aim for reuse.
  • Write the description to say what the skill does and when to use it, because that is all the agent sees at startup.
  • Define clear stages and exit conditions.
  • Test against real tasks and revise from observed failures.
Risks
  • A third-party skill can include scripts. Treat it as code: review it and limit what it can access.
  • A vague description means the skill is never loaded, or is loaded for the wrong task.
  • Skills go stale when the process changes, so give each an owner and a review cycle.
Model Context Protocol (MCP)A standard way to reach tools and live systems
What it is, and the problem it solves
MCP is an open standard, introduced by Anthropic in November 2024, for connecting agents to tools, data sources and resources. Without it, every pairing of application and tool needed a custom connector (the “N × M” problem). A shared standard needs only N + M implementations.
How it works
An MCP host is the application that uses the tools. An MCP client inside the host keeps the connection to an MCP server, which discovers, executes and returns results for tools. Messages use JSON-RPC 2.0, over stdio for local servers and streamable HTTP for remote ones. Servers can also expose resources (data to read) and prompts (reusable templates). A registry acts as a service directory for public servers.
In the enterprise
Servers carry the responsibility for security, scalability and governance, and several features are still maturing.
  • Authentication and authorization: an OAuth-based approach for remote servers was added during 2025 and keeps being revised, so check the current specification.
  • Identity: prefer delegated user identity and scoped, short-lived credentials over shared service keys.
  • Observability: support is evolving, so add your own tracing of tool calls.
Risks
  • Prompt injection through tool descriptions or tool results.
  • Over-privileged tokens and tools that can do more than the task needs.
  • Unvetted third-party servers.
  • Tool sprawl: many tool definitions in context raise cost and lower accuracy.
Retrieval-Augmented Generation (RAG)Relevant knowledge at query time
What it is, and the problem it solves
RAG connects an LLM to external data so it retrieves relevant information at query time. Models only know what they were trained on, and their context windows are limited. RAG lets them use current and private knowledge, and supplies only the relevant pieces.
How it works
Five stages: data collection, chunking and embedding, indexing, retrieval and generation. The first three happen ahead of time. Vector databases (Pinecone, ChromaDB, FAISS, Weaviate) run fast approximate nearest-neighbour search, and frameworks such as LangChain and LlamaIndex help embed the data. At query time the system retrieves chunks by semantic search, combines them with the instructions and question, and the LLM answers from them. Variants: agentic RAG (the agent decides when and what to retrieve), GraphRAG (knowledge graphs) and multimodal RAG (images, tables, diagrams).
In the enterprise
Most RAG quality comes from retrieval, not the model.
  • Combine semantic and keyword search, then rerank to the best few chunks.
  • Keep source, date, owner and type with each chunk for filtering and citations.
  • Enforce permissions at retrieval time.
  • Re-index when documents change and remove outdated ones.
  • Test on real questions, measuring retrieval quality and answer faithfulness separately.
  • If the whole knowledge base fits in the context window, including it directly can be simpler.
Risks
  • Wrong chunks retrieved, or the right one buried among irrelevant ones.
  • Stale or conflicting documents produce confident wrong answers.
  • Unenforced permissions leak restricted content.
  • Retrieved text can carry hijacking instructions, so treat it as untrusted data.
MemoryContinuity across sessions
What it is, and the problem it solves
Memory captures and consolidates key information across sessions. A session is the raw record of one conversation, and memory is the condensed, durable part worth keeping. RAG makes an agent knowledgeable about an organization’s content, while memory makes it familiar with the individual user and earlier work. Without it every conversation starts from zero and long ones outgrow the context window. Memory enables personalization, context window management, insight across many users (aggregated and privacy-preserving) and self-improvement from strategies that worked.
How it works
Common types are semantic (facts and preferences), episodic (past interactions) and procedural (learned ways of doing things). The pipeline: extract what is worth keeping, consolidate it (merge duplicates, resolve conflicts, drop outdated items), store it with metadata, retrieve what is relevant and inject it into the context. Frameworks such as ADK and LangGraph provide the plumbing, but long-term storage still needs developer logic.
In the enterprise
  • Scope: decide whether a memory belongs to a user, team, tenant or task, and keep them separate.
  • User control: let users view, correct and delete memories, and set retention limits.
  • Privacy: apply the same classification, access control and compliance rules as other enterprise data.
Risks
  • Wrong or outdated memories reused with confidence.
  • Poisoned memory: malicious or mistaken content saved and later acted on.
  • Over-personalization, or memory shown where it does not belong.

Governance and observabilityQuestions to answer before enterprise rollout
  • Ownership and lifecycle: who creates, reviews, versions and retires each skill, MCP server, knowledge source and memory store.
  • Access control: enforce per-user permissions at the retrieval and tool level, not only in the prompt.
  • Traceability: for each answer, log which skill version loaded, which tools were called, which chunks were retrieved and which memories were injected. This is what lets you explain a decision.
  • Evaluation: keep regression tests for skills, retrieval quality checks for RAG and accuracy reviews for memory, and run them on every change.
  • Monitoring: track usage, latency, cost and error rates, and detect hallucinations and failed tool calls.
  • Security and compliance: vet third-party skills and MCP servers, guard against prompt injection, apply least privilege, keep audit trails and retention rules. A registry or approval process helps.

In short, Skills supply the procedure, MCP the tools, RAG the facts and Memory the continuity. Match each to the problem it solves, start simple, and know who owns each piece, who can access it and which pieces shaped each decision.
